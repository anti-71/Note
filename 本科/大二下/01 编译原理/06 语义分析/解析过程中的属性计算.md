##### 解析过程中的属性计算

---

##### 语法制导翻译概述

**语法制导的翻译方案（Syntax-Directed Translation, SDT）** 是将语义动作嵌入到文法产生式的**合适位置**，使得在语法分析过程中可以**即时**计算属性

- SDT 不需要在语法分析完成后额外遍历 AST，而是将属性计算**融合**进解析和规约过程
- SDT 的关键在于为每个产生式确定**语义动作插入的位置**

> [!abstract] 核心思想：**在解析完成时就已得到所有必要的语义信息**，不额外浪费遍历

---

##### SDT 的语义动作位置

对于产生式 $A \to X_1 X_2 \dots X_n$，语义动作可安插在：

1. **产生式末尾** — 在全部右部符号匹配完毕后触发（适合综合属性）
2. **产生式中间** — 在部分右部符号匹配后触发（适合继承属性、符号表插入等）

```
SDT 示例（后缀表达式求值）：
──────────────────────────
E → E₁ + T    { print('+') }
E → T
T → num       { print(num.lexval) }
```

> [!note] 语义动作的位置决定了它何时执行，这与**属性计算的方向**直接相关

---

##### 语义动作与解析栈的配合

**在自底向上解析中**：
- 分析栈中的每个状态/符号都关联一个**属性值栈**
- 在**规约**时触发产生式末尾的语义动作，从属性值栈中弹出右部符号的属性，计算后压入左部符号的属性

```
LR 分析中的属性栈操作：

步骤 1: 读入 num (值 = 3)，压栈
步骤 2: 按 T → num 规约
        → 弹出 num.lexval (=3)，计算 T.val = 3，压栈
步骤 3: 读入 +，压栈
步骤 4: 读入 num (值 = 5)，压栈
步骤 5: 按 T → num 规约
        → 弹出 num.lexval (=5)，计算 T.val = 5，压栈
步骤 6: 按 E → E + T 规约
        → 弹出 T.val (=5) 和 E₁.val (=3)，
          计算 E.val = 3 + 5 = 8，压栈
```

---

##### 不同解析策略中的属性计算

| 解析策略 | 支持的属性类别 | 实现方式 |
|:---:|:---:|:---:|
| **LL 解析（自顶向下）** | L-属性文法 | 在扩展非终结符前计算继承属性并传递 |
| **LR 解析（自底向上）** | S-属性文法（可模拟部分继承属性） | 在规约时计算综合属性 |
| **递归下降（手写）** | L-属性文法 | 函数参数传递继承属性，返回值传递综合属性 |

---

##### 在 LL 解析中计算属性

**LL 自顶向下解析**天然适合 **L-属性文法**：

- 在扩展非终结符 $A$ 为产生式 $A \to X_1 X_2 \dots X_n$ 时，按顺序处理每一个右部符号
- 处理 $X_j$ 前，已经得到了 $A$ 的继承属性和 $X_1 \dots X_{j-1}$ 的属性，因此 L-属性文法所需的继承属性都在此可用

```
LL 解析中的属性传递（带类型检查的声明）：
────────────────────────────────────
D → T L               { L.inh = T.type }
T → int               { T.type = integer }
T → float             { T.type = float }
L → L₁ , id           { L₁.inh = L.inh; id.type = L.inh }
L → id                { id.type = L.inh }
```

---

##### 在 LR 解析中模拟继承属性

**LR 自底向上解析**原生只支持**综合属性**，但可通过以下技巧**模拟继承属性**：

1. **改写文法** — 将继承属性转化为综合属性
2. **使用全局符号表** — 通过全局可变状态模拟继承属性的传递
3. **中间动作（Mid-Rule Action）** — 在产生式中间插入语义动作（Yacc 支持以 `/* empty */` 规则实现）

> [!warning] 在 LR 框架中使用中间动作需要特别注意：中间动作会在分析栈中占据一个"虚拟"位置，必须正确管理属性值栈的索引

```
Yacc 中通过中间动作模拟继承属性：
────────────────────────────────
decl: type id_list
        { /* 继承属性已通过全局符号传递 */ }
    ;

type: INT    { current_type = INT; }
    | FLOAT  { current_type = FLOAT; }
    ;
```

##### 解析时属性计算的优缺点

| 优点 | 缺点 |
|:---|:---|
| **单遍完成** — 语法分析结束时属性已全部计算完毕 | **文法改写需求** — 有些语义动作需通过改写文法来配合 |
| **效率高** — 无需额外的 AST 遍历开销 | **调试困难** — 语义动作与解析逻辑交错，错误定位较难 |
| **实现简单** — 适合 Yacc/Bison 等工具 | **工具限制** — 不同解析器生成器对语义动作的支持各有差异 |

---

##### 解析树 vs. AST 中的属性计算

| 维度 | 解析时计算（SDT） | AST 遍历计算 |
|:---:|:---|:---:|
| 数据结构 | 不显式存储树 | 显式构建 AST |
| 属性存储 | 解析栈 + 全局状态 | AST 节点中的字段 |
| 遍历次数 | 单遍（融合在解析过程中） | 1+ 次（额外的树遍历） |
| 灵活性 | 低，受解析顺序限制 | 高，可按任意顺序遍历 |
| 典型工具 | Yacc, Bison, ANTLR | Visitor 模式手写 |

> [!tip] 现代编译器中，将**解析**与**语义分析**完全分离的纯 AST 遍历方案逐渐增多（如 Rust 的 `rustc`、Go 的 `gc`），这得益于 AST 遍历的灵活性和可维护性方面的优势
