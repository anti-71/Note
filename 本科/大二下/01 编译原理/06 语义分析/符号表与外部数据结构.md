##### 符号表与外部数据结构

##### 符号表的作用

**符号表（Symbol Table）** 是编译器用于存储程序中各标识符相关信息的核心数据结构在语义分析阶段，符号表扮演**"全局黑板"**的角色——各语义动作在其中查询和记录信息

> [!abstract] 符号表记录了每个标识符的**声明信息**，包括但不限于：

---

##### 符号表的操作

| 操作 | 说明 | 调用时机 |
|:---|:---|:---|
| **insert(name, info)** | 将新标识符及其属性插入符号表 | 处理声明语句时 |
| **lookup(name)** | 按名称查找标识符，返回其属性 | 处理引用（使用）标识符时 |
| **delete(scope)** | 退出某作用域时删除该作用域的所有符号 | 离开作用域时 |
| **modify(name, info)** | 更新已有符号的属性 | 处理后续声明信息（如类型完善） |

---

##### 符号表的常见实现方式

| 数据结构 | 插入 | 查找 | 删除 | 适用场景 |
|:---:|:---:|:---:|:---:|:---|
| **链表（Linear List）** | $O(1)$ 头部 | $O(n)$ | $O(n)$ | 小型程序、简短作用域 |
| **哈希表（Hash Table）** | $O(1)$ 均摊 | $O(1)$ 均摊 | $O(1)$ | 通用、高效 |
| **平衡树（BST / 红黑树）** | $O(\log n)$ | $O(\log n)$ | $O(\log n)$ | 需要有序遍历时 |
| **字典（Trie / 散列词组）** | $O(key\_len)$ | $O(key\_len)$ | $O(key\_len)$ | 长标识符名称 |

> [!tip] 大多数编译器使用 **哈希表** 实现符号表，配合 **作用域栈（scope stack）** 处理嵌套作用域

##### 作用域管理

**嵌套作用域**（如 C/Java 中的块结构 `{ ... }`）的管理需要符号表支持**作用域的进入与退出**：

**方案一：独立符号表**
- 每个作用域维护独立的符号表
- 进入新作用域时创建新表，退出时销毁
- 查找时从当前作用域开始，逐级向上层作用域搜索

**方案二：统一符号表 + 作用域栈**
- 一个全局符号表，每条记录附带作用域编号
- 维护一个**作用域栈（Scope Stack）**，记录当前活跃作用域
- 插入时标记当前作用域编号，查找时按作用域由内到外搜索

```
作用域栈示例：
────────────────────────
Stack top → 作用域 3: { 局部变量 k, m }
             作用域 2: { 参数 x, y }
Stack base → 作用域 1: { 全局变量 a, b, c }
```

> [!note] 统一符号表的实现更常见，因为它便于在语义分析和中间代码生成之间共享符号信息

##### 属性作为参数与返回值

属性文法的另一种实现策略是将属性视为**函数的参数和返回值**：

- **综合属性** → 函数的**返回值**（return value）
- **继承属性** → 函数的**参数**（parameter）

```
// 示例：用函数模拟属性计算
int E_val(Environment env, Tree t) {
    // env: 传入的继承属性（环境）
    // return: 综合属性 val
    if (t->op == PLUS) {
        int left_val = E_val(env, t->left);
        int right_val = T_val(env, t->right);
        return left_val + right_val;
    }
    // ...
}
```

这种视角使属性计算可以与**纯函数式实现**对应，便于形式化推理

##### 符号表作为外部数据结构

在许多实际编译器中，符号表并非属性文法的正式组成部分，而是作为一种**外部数据结构**独立存在：

```
    ┌─────────────────┐
    │   属性文法      │  ← 形式化描述：理论上属性通过依赖图传递
    │  (理论模型)     │
    └────────┬────────┘
             │ 工程实现
             ▼
    ┌─────────────────┐
    │  符号表 + AST   │  ← 工程实现：通过符号表全局共享信息
    │  (实际实现)     │
    └─────────────────┘
```

- 将符号表作为全局可变数据结构操作，可避免在 AST 节点之间显式传递大量继承属性
- 缺点是**降低了语义动作的局部性**——符号表的修改必须小心控制顺序，否则可能导致不一致

> [!warning] 符号表作为外部可变状态时，需要格外注意**语义动作的执行顺序**：若在左侧子节点的语义动作中修改了符号表，右侧子节点的语义动作将观察到修改后的状态——这实际上是**通过副作用隐式传递继承属性**

---

##### 符号表的设计权衡

| 设计选择 | 优势 | 劣势 |
|:---|:---|:---|
| 属性文法（纯属性传递） | 形式化、无副作用 | 需要显式传递大量属性，AST 节点变"胖" |
| 符号表 + 副作用 | 简洁高效、AST 节点轻量 | 全局状态、依赖执行顺序、调试困难 |
| 混合方式 | 灵活性高 | 需要在两者之间找到平衡 |

> [!abstract] 实际编译器普遍采用 **混合方式**：将**类型信息**等全局数据存入符号表，而将**局部计算值**（如表达式值）作为综合属性沿 AST 传递
